**Дата аудита:** 2026-09-28
**Ветка:** `master` (в репозитории **нет ни одного коммита** — всё содержимое находится в staging/untracked)
**Режим аудита:** только чтение, код не изменялся.

## 1. Краткое резюме

Проект — рабочее Next.js 16 / React 19 приложение для записи к косметологу с публичным лендингом, полноценной админ-панелью и CRM клиентов; на момент аудита запущенный инстанс (`next start`, порт 3000, PID 6128) отвечает и отдаёт данные, так что «в целом оно работает». Код аккуратный, единообразный, типизированный, с zod-валидацией на всех точках входа и без единого XSS-вектора (`dangerouslySetInnerHTML`/`eval` отсутствуют), ESLint проходит чисто. При этом **свежая сборка сейчас падает** — `npm run build` и `npm run typecheck` обрываются на повреждённом сгенерированном файле `.next/dev/types/routes.d.ts`, который подтягивается через `next-env.d.ts`.

Главная архитектурная особенность и одновременно главный риск — хранилище: вместо БД используется один файл `storage/app-data.json` (110 КБ), который целиком перечитывается и перезаписывается на каждую операцию. Отсюда растут две реальные проблемы: гонка при одновременной записи (двойное бронирование одного слота технически возможно — проверка слота и его сохранение не атомарны) и невозможность горизонтального масштабирования из-за in-memory кэша.

Безопасность — слабое место. Telegram-webhook при отсутствии `TELEGRAM_WEBHOOK_SECRET` **вообще не проверяет отправителя**, то есть кто угодно может подтверждать и отменять чужие записи. Админ-сессия — это не сессия, а статичный хэш `sha256(пароль:секрет)`, который не ротируется и не отзывается, плюс существует постоянный обходной путь через заголовок `x-admin-password` без какого-либо rate-limiting. Медицинские фото клиентов (до/после) складываются в `public/uploads/clients/` и **скачиваются без авторизации** — проверено, отдаётся HTTP 200 и 3 МБ PNG.

Логических багов тоже хватает: при интеграции с Google Calendar занятые интервалы парсятся как локальное время, хотя freeBusy возвращает UTC — сдвиг на 4 часа; в сценарии «предложить другое время» из Telegram список слотов строится от `booking.date`, а выбранный слот ищется в списке от `booking.date + 1 день`, то есть клиенту уходит **не тот слот**, который выбрал врач; в прошлое записаться можно (серверная проверка «слот в будущем» отсутствует, а «сегодня» берётся из браузера клиента).

Модуль SMS спроектирован грамотно (очередь + лог + шаблоны + адаптеры провайдеров + двойной предохранитель автоотправки), но **не отправил ни одного сообщения**: в очереди 19 записей, все в статусе `scheduled` с `attempts: 0`, лог отправок пуст. Причина двойная — выбранный в `.env.local` провайдер `gsm` является заглушкой, которая всегда возвращает ошибку, и в системе **нет планировщика**, который забирал бы отложенные задания из очереди.

Тестов нет вообще — ни unit, ни e2e, ни конфигов тестовых раннеров. `npm audit` для production-зависимостей показывает 9 уязвимостей, включая **critical в самом Next.js** и high в `xlsx`, для которого фикса не существует.

### 2.2. Точки входа и запуск


### 2.3. Слоистость

```
src/app/api/**/route.ts      → HTTP-слой: zod-валидация + requireAdmin + errorResponse
  └── src/lib/bookings/*     → бизнес-сценарии (create/confirm/cancel/reschedule/change)
       ├── src/lib/availability/*  → расчёт свободных слотов
       ├── src/lib/sms/*           → очередь, шаблоны, провайдеры SMS
       ├── src/lib/telegram/*      → отправка/редактирование сообщений бота
       ├── src/lib/google/*        → Google Calendar (JWT-подпись вручную, без SDK)
       └── src/lib/repositories/*  → доступ к app-data.json
```

Разделение выдержано корректно: маршруты не лезут в репозитории напрямую мимо сценариев, побочные эффекты (Telegram/Google/SMS) обёрнуты в try/catch и возвращаются как `warnings`, а не рушат основную операцию. Это хорошая практика, реализованная последовательно.

### 2.4. Хранилище данных

`appRepository` (`src/lib/repositories/appRepository.ts`):
- `memoryCache` (строка 18) — весь датасет в памяти процесса;
- `updateQueue` (строка 19) — последовательное выполнение записей через цепочку промисов;
- `writeData` (строки 87–93) — атомарная запись через временный файл + `rename`;
- `mergeWithDefaults` (строки 39–69) — подстановка дефолтов и эвристика `containsMojibake` для отлова битой кодировки.

Реализация для файлового хранилища сделана хорошо, но фундаментальные ограничения остаются (см. §4 и §9).

## 4. Найденные ошибки

### 🔴 Критичные

---

**#1 — Свежая сборка проекта падает**

`.next/dev/types/routes.d.ts` (строка 98) — сгенерированный Next.js файл повреждён: содержимое склеено из двух записей, строка начинается обрывком `iv>{props.children}</div>`. Файл подключается директивой `import "./.next/dev/types/routes.d.ts";` в `next-env.d.ts:3`, а `tsconfig.json` включает `.next/dev/types/**/*.ts`, поэтому ошибка попадает и в `npm run build`, и в `npm run typecheck`.

Фактический вывод:

```
✓ Compiled successfully in 5.4s
  Running TypeScript ...
Failed to type check.
.next/dev/types/routes.d.ts:98:10
Type error: ',' expected.
Next.js build worker exited with code: 1
```

Исходный код при этом корректен: сама компиляция проходит, ESLint чист. Лечится удалением каталога `.next`. **На момент аудита удалить его не удалось** — каталог занят работающим процессом `next start` (PID 6128, слушает :3000). То есть текущий запущенный инстанс собран раньше и работает, но повторить сборку с нуля нельзя, пока кэш не очищен.

**#2 — Telegram-webhook без секрета открыт для всех**

`src/app/api/telegram/webhook/route.ts:29-34`

```ts
const configuredSecret = process.env.TELEGRAM_WEBHOOK_SECRET;
const receivedSecret = request.headers.get("x-telegram-bot-api-secret-token");

if (configuredSecret && receivedSecret !== configuredSecret) {
  return NextResponse.json({ success: false, message: "Unauthorized" }, { status: 401 });
}
```

Условие `configuredSecret &&` означает: если переменная окружения не задана (или задана пустой строкой), проверка **полностью пропускается**. Любой, кто отправит POST на `/api/telegram/webhook` с телом `{"callback_query":{"id":"1","data":"booking_cancel:booking_<id>"}}`, отменит чужую запись, подтвердит её или инициирует перенос. Идентификаторы записей предсказуемы по формату (`booking_<uuid>`), но UUID подобрать нельзя — тем не менее, они утекают в публичный ответ `/api/booking` (см. баг #12), так что свою же запись злоумышленник подтвердит сам, минуя врача.

В текущем `.env.local` секрет задан, поэтому дыра закрыта *конфигурацией, а не кодом*. Любой деплой с забытой переменной откроет её мгновенно.

**#3 — Гонка: возможна двойная запись на один слот**

`src/lib/bookings/createBookingRequest.ts:40-93`

```ts
const availability = await assertSlotIsAvailable({...});  // строка 40 — ЧТЕНИЕ
// ... 50 строк: upsert клиента, сборка объекта booking ...
await appRepository.saveBooking(booking);                 // строка 93 — ЗАПИСЬ
```

Проверка занятости и сохранение — две независимые асинхронные операции. `appRepository.updateData` сериализует только *записи* (`updateQueue`, строка 19), но не связку «проверил → записал». Два одновременных POST `/api/booking` на один и тот же слот оба пройдут проверку (оба читают состояние до записи) и оба сохранятся.

Тот же паттерн повторяется в `createManualBooking.ts:24-60`, `changeBookingDateTime.ts:33-42`, `confirmBooking.ts:31-53`, `updateBookingDetails.ts:64-81`.

В текущих данных пересечений нет (проверено программно: 0 перекрытий среди 29 записей) — трафик слишком мал. С ростом нагрузки баг проявится.

**#4 — Медицинские фото клиентов доступны публично без авторизации**

`src/lib/clients/clientPhotoStorage.ts:59-69`

```ts
const fileName = `${sanitizeClientId(clientId)}_${Date.now()}_${randomUUID().slice(0, 8)}${extension}`;
const targetPath = path.join(uploadDirectory, fileName);   // public/uploads/clients/
// TODO: Replace local uploads with cloud storage before production.   ← строка 62
await writeFile(targetPath, buffer);
return { fileName, url: `/uploads/clients/${fileName}` };
```

Каталог `public/uploads/clients/` раздаётся Next.js как статика — без cookie, без `requireAdmin`, без каких-либо проверок. Проверено на работающем инстансе:

```
GET /uploads/clients/client_76aefe63-...-936896629507_1780573162538_e523d86a.png
→ 200 image/png 3002598 байт
```

Это фотографии «до/после» — медицинские персональные данные. Имя файла содержит **реальный `clientId`**, поэтому URL не является непредсказуемым в полном смысле: зная id клиента (а он утекает в ответах админских API и в экспортах), остаётся подобрать timestamp + 8 hex-символов. Кроме того, такие URL попадают в логи прокси, историю браузера и Referer.

Аналогично `public/uploads/portfolio/` — но там публичность и задумана.

**#6 — Google Calendar: занятость считается со сдвигом на 4 часа**

`src/lib/google/googleCalendarProvider.ts:71-75`

```ts
const toTimeSlot = (start: string, end: string): TimeSlot => ({
  date: start.slice(0, 10),
  startTime: start.slice(11, 16),
  endTime: end.slice(11, 16)
});
```

Google Calendar API `freeBusy` возвращает интервалы в RFC3339 **в UTC** (`2026-09-28T09:00:00Z`), независимо от переданного `timeZone`. Код просто вырезает символы 11–16, получая **время UTC**, и сравнивает его с локальными рабочими часами (Asia/Yerevan, UTC+4). Итог: событие 13:00–14:00 по Еревану блокирует слот 09:00–10:00 в системе. Занятые часы блокируются не те, реально занятые остаются открытыми — прямой путь к наложению приёмов.

Сопутствующие дефекты той же функции: событие, пересекающее полночь, схлопывается в некорректный интервал (`endTime` < `startTime`); многодневные события учитываются только по дате начала.

Отмечу, что `toDateTime` (строка 69) при **создании** события жёстко подставляет `+04:00`. Для Армении это корректно (постоянный UTC+4 без перехода на летнее время), но значение захардкожено и не переживёт смену часового пояса клиники.

В `.env.local` стоит `GOOGLE_CALENDAR_ENABLED=true` и заполнены service-account credentials — **баг активен в текущей конфигурации**.

## 5. Безопасность (сводно)

### 5.1. Авторизация и разграничение прав

**Ролевая модель фактически бинарная:** «админ» и «все остальные». Ролей сотрудников, разграничения прав внутри админки, аудита действий — нет. Заявленные в задании «функции для участников/сотрудников» в коде отсутствуют.

**Положительное:** все 30 админских route-хендлеров вызывают `requireAdmin(request)` — проверено поимённо по каждому файлу, пропусков нет. Это сделано дисциплинированно.

**Проблемы:** см. баги #2 (webhook без секрета), #9 (статичный токен, backdoor-заголовок, dev-пароль `admin`, отсутствие rate-limit), #10 (нет серверного guard'а страниц).

### 5.2. Хранение паролей

Пароль администратора хранится **в открытом виде** в переменной окружения `ADMIN_PASSWORD` и сравнивается напрямую (`src/app/api/admin/login/route.ts:7`). Хэширования (bcrypt/argon2) нет. Для схемы «один администратор, пароль только в env» это допустимый компромисс, но:
- стойкость пароля ничем не проверяется (нет требований к длине и сложности);
- при добавлении второго пользователя схема не расширяется;
- `getAdminPassword()` вызывается на каждом запросе и хэшируется заново (`auth.ts:19`).

Паролей клиентов не существует — регистрации клиентов нет.

### 5.3. SQL-инъекции

**Неприменимо** — SQL-базы нет. Все операции — работа с JS-объектами в памяти + `JSON.parse`/`JSON.stringify`.

Косвенный аналог — **prototype pollution**: `JSON.parse` в `appRepository.readData` (строка 78) применяется к файлу, который наполняется в том числе импортом из Excel (`xlsx`, см. #20) и не проходит валидацию схемой при чтении. Ключи `__proto__` в данных теоретически способны загрязнить прототип при последующих spread-операциях. Валидация `AppData` через zod при загрузке закрыла бы вопрос.

### 5.4. XSS

Векторов не обнаружено. `dangerouslySetInnerHTML`, `innerHTML`, `eval`, `new Function` в `src/` отсутствуют полностью (проверено поиском). React экранирует весь пользовательский ввод автоматически.

Потенциальная точка внимания: `portfolioItemSchema.imageUrl` (`src/lib/validation/schemas.ts:85`) валидируется как `z.string().min(1)` без проверки на схему URL. Значение попадает в `next/image`, который отвергнет `javascript:`, так что эксплуатация маловероятна, но валидацию стоит ужесточить.

### 5.6. Секреты и ключи API

**Хардкода секретов в исходниках нет** — все читаются из `process.env`. Это сделано правильно.

Замечания:
1. `.env.local` содержит **боевые секреты** в рабочем каталоге: реальный токен Telegram-бота, `TELEGRAM_CHAT_ID`, `TELEGRAM_WEBHOOK_SECRET`, `GOOGLE_PRIVATE_KEY` (приватный ключ service-account целиком) и пароль администратора.

3. Тем не менее файл лежит в незашифрованном виде рядом с проектом и попадает в любой бэкап каталога. Для production ключи следует держать в секрет-хранилище платформы.
4. `"local-admin-secret"` — захардкоженный fallback-секрет (`src/lib/admin/auth.ts:13`). Строка присутствует в исходниках и известна каждому, у кого есть доступ к коду.

### 5.7. Загрузка файлов

Реализована **аккуратно** (`clientPhotoStorage.ts`, `portfolioImageStorage.ts`):
- whitelist MIME → расширение (jpeg/png/webp);
- проверка **magic bytes** (сигнатуры файла), а не только заголовка `Content-Type`;
- лимит 5 МБ;
- имя файла генерируется сервером, пользовательское не используется → path traversal невозможен;
- `deleteClientPhotoFile` применяет `path.basename` (строка 73);
- при ошибке после записи файл удаляется (`photos/route.ts:106-108`).

Единственная — но критичная — проблема: **место хранения** (`public/`, см. баг #4). Также отсутствует перекодирование изображений (EXIF-метаданные, включая GPS-координаты съёмки, сохраняются в файле).

### 5.8. Прочее

- **CSRF:** cookie выставлена с `sameSite: "lax"` (`auth.ts:27`), что защищает от межсайтовых POST. Дополнительных токенов нет — приемлемо.
- **Cookie:** `httpOnly: true`, `secure` только в production (`auth.ts:26-28`) — корректно.
- **Security headers:** `next.config.mjs` не задаёт CSP, `X-Frame-Options`, `Referrer-Policy`, HSTS.
- **Логирование:** секреты в логи не пишутся. `console.info` в mock-провайдерах выводит **тексты SMS и номера телефонов** (`providers.ts:41-45`) — персональные данные в логах сервера.

### 8.4. Как хранится телефон клиента

**Нормализация** — `src/lib/phone/armenianPhone.ts`, функция `normalizePhoneNumber`:
- приводит к E.164 (`+374XXXXXXXX`);
- `+` → международный формат с сохранением кода страны;
- `00` → `+`;
- локальные армянские формы (`0XXXXXXXX`, 8 цифр, `374XXXXXXXX`) → `+374`;
- иначе — международный номер без `+`;
- невалидный → `null`.

**Где хранится:**

| Поле | Тип | Что содержит |
|---|---|---|
| `Client.phone` | `string` | исходный ввод |
| `Client.normalizedPhone` | `string` | E.164 — ключ дедупликации клиентов |
| `Booking.phone` | `string` | нормализованный (`bookingRequestSchema` трансформирует на входе) |
| `SmsQueueItem.phone` | `string` | нормализованный повторно в `enqueueSms:185` |
| `SmsLog.phone` | `string` | как в очереди |

**Оценка:** нормализация сделана качественно и применяется последовательно — и на клиенте (`BookingForm.tsx:240`), и на сервере (`schemas.ts:13-28`). **Номер в очереди и логе дублируется от клиента** — при смене номера старые записи очереди уйдут на прежний. Для перехода на мультиканальность это как раз плюс: денормализованный «адрес получателя» — правильная модель.

```ts
  nextAttemptAt?: string;            // ← НОВОЕ: для ретраев с backoff
  fallbackOf?: string;               // ← НОВОЕ: id исходного элемента при переотправке в другой канал
  lastError?: string;
  providerMessageId?: string;
  createdAt: string; updatedAt: string; sentAt?: string;
};
```

Миграция данных: `channel: "sms"`, `recipient = phone` для всех существующих элементов — выполняется одноразовым скриптом в `scripts/` либо прямо в `mergeWithDefaults` (`appRepository.ts:39-69`), где уже есть подобная нормализация.

#### Шаг 2. Хранить контакты и предпочтение канала в клиенте

Расширить `Client` (`src/types/domain.ts:67-90`):

```ts
export type ClientContacts = {
  phone: string;                       // уже есть, E.164 — канал sms
  viberId?: string;                    // обычно тот же номер в E.164
  telegramChatId?: string;             // получается только после /start у бота
};

export type Client = {
  // ...существующие поля
  preferredChannel?: NotificationChannel;      // что выбрал клиент
  channelOptIn?: Partial<Record<NotificationChannel, boolean>>;  // согласие
  telegramChatId?: string;
  telegramLinkToken?: string;          // одноразовый токен для привязки бота
};
```

**Важное ограничение, которое нужно заложить в UX сейчас:** Telegram-бот **не может написать первым**. Пока клиент не нажал `/start` у бота, `telegramChatId` неизвестен и отправка невозможна. Значит форма записи не может просто «предложить Telegram» — она должна:
1. сохранить предпочтение `telegram`;
2. показать deep-link `https://t.me/<bot>?start=<одноразовый токен>`;
3. поймать `message.text === "/start <token>"` в вебхуке, сопоставить токен с клиентом и записать `chat.id`;
4. **до момента привязки использовать SMS как фолбэк.**

Viber аналогично требует, чтобы пользователь подписался на паблик-аккаунт (Viber Business Messages), либо использования платного канала Viber Business API через провайдера-агрегатора. Это решение уровня бизнеса, а не кода — его нужно принять до реализации.

#### Шаг 4. Выбор канала с фолбэком в сервисе

Единственное содержательное изменение в `smsService.ts` → `notificationService.ts`:

```ts
const resolveChannel = (
  client: Client | undefined,
  requested?: NotificationChannel
): { channel: NotificationChannel; recipient: string } => {
  const candidates: NotificationChannel[] = [
    requested,
    client?.preferredChannel,
    "sms"                                  // конечный фолбэк
  ].filter(Boolean) as NotificationChannel[];

  for (const channel of candidates) {
    if (client?.channelOptIn?.[channel] === false) continue;   // отписка
    const recipient = recipientFor(client, channel);
    if (recipient && resolveProvider(channel).isConfigured()) {
      return { channel, recipient };
    }
  }
  return { channel: "sms", recipient: client?.normalizedPhone ?? "" };
};
```

Правило фолбэка: **если предпочтительный канал не доставил — переотправить по SMS**, создав новый элемент очереди с `fallbackOf: <исходный id>`. Это делает мультиканальность безопасной: сбой Telegram/Viber не оставит клиента без уведомления.

Вся остальная логика (`dedupe`, `isDispatchAllowed`, `appendLog`, `cancelBookingScheduledSms`) **не меняется** — она уже каналонезависима. Дедупликацию стоит расширить ключом `(bookingId, type, channel)`.

#### Шаг 5. Планировщик очереди — обязательное недостающее звено

Без него мультиканальность бессмысленна, поэтому это первоочередная задача **до** любых новых каналов.

Перед этим — привести `scheduledAt` к единому формату UTC ISO (исправить `reminderDateTime`, `smsService.ts:368-376`, баг #11), иначе планировщик будет срабатывать не вовремя.

Три варианта реализации, по возрастанию надёжности:

1. **Внешний cron → защищённый эндпоинт.** Добавить `POST /api/notifications/dispatch` с авторизацией по секрету (`CRON_SECRET`), который выбирает из очереди все `scheduled` с `scheduledAt <= now` и отправляет. Дёргать системным cron/Task Scheduler раз в 5 минут. Минимум кода, работает на любом хостинге. **Рекомендуемый вариант для текущего масштаба.**
2. **Vercel Cron / GitHub Actions** — то же самое, но триггер снаружи.
3. **Внутренний воркер** (`setInterval` при старте сервера) — проще всего, но при нескольких инстансах даст дубли отправок и не переживает перезапуск. Не рекомендую, пока хранилище файловое.

Добавить экспоненциальный backoff: `nextAttemptAt = now + 2^attempts минут`, максимум 5 попыток, затем `failed` навсегда.

## 9. Рекомендации по улучшению

### 9.1. Хранилище

Файловый репозиторий выработал ресурс. `README` уже предполагает миграцию («ready to be replaced with Prisma/PostgreSQL») — её стоит выполнить до наращивания функционала. Что это даст помимо производительности:

- **Транзакции** закроют гонку двойного бронирования (баг #3) одним `SELECT … FOR UPDATE` или уникальным индексом-ограничением на пересечение интервалов (`EXCLUDE USING gist` в PostgreSQL решает задачу декларативно).
- **Внешние ключи** предотвратят удаление услуги, на которую ссылаются записи (баг #13).
- **Горизонтальное масштабирование** и корректная работа на serverless.
- **Индексы** вместо линейного перебора массивов.

Слой `src/lib/repositories/*` уже изолирует доступ к данным — миграция затронет только его. Это заслуга текущей архитектуры.

Если миграция откладывается — минимум: обернуть связку «проверка слота → сохранение» в единый `updateData`-колбэк, чтобы она выполнялась внутри сериализующей очереди.

### 9.2. Время и часовые пояса

Ввести единое правило и вынести его в модуль `src/lib/time/`:
- **в хранилище — только UTC ISO** с суффиксом `Z`;
- **бизнес-логика расписания — в `Asia/Yerevan`**, зона берётся из настроек, а не из захардкоженного `+04:00`;
- **«сегодня» определяет сервер**, не браузер;
- конверсия — через `Intl.DateTimeFormat` с `timeZone` или `date-fns-tz` / `Temporal`.

Это закроет баги #6, #8, #11 и снимет класс проблем целиком.

## 11. Что проверить не удалось

Честный перечень ограничений аудита:

1. **Реальная отправка SMS** — провайдер `gsm` является заглушкой, GSM-модем/шлюз физически не подключён. Проверить фактическую доставку невозможно.
